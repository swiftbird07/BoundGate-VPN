# TPM 2.0 device keys (M6)

With `key_kind: tpm2` a node's identity key is created inside a TPM 2.0 and
never exists anywhere else. Everything above it is unchanged: the same
self-signed device certificate, the same SPKI fingerprint, the same mTLS.
Only the signing moves from a file into the chip.

```yaml
key_kind: tpm2
# tpm_device: /dev/tpmrm0                 # default: the kernel's TPM resource manager
# tpm_device: unix:/run/swtpm/tpm.sock    # a software TPM (swtpm) on a stream socket; also tcp:HOST:PORT
```

## What happens

* **Key.** ECDSA P-256, signing only, scheme fixed to SHA-256, created by
  `TPM2_Create` with `fixedTPM`, `fixedParent` and `sensitiveDataOrigin`:
  generated by the TPM, not importable, not duplicable to another TPM. No
  password: the key binds the machine, the person is OIDC's matter.
* **Parent.** The storage root key, derived from the owner hierarchy with
  the TCG reference template (ECC P-256 SRK). It is recreated at every
  start and yields the same key as long as the TPM's owner seed is the same.
* **On disk.** `<state_dir>/device.tpm` (0600): the public area and the
  private blob *wrapped by that SRK*. On any other TPM `TPM2_Load` refuses
  it ("was device.tpm created on this TPM?"). Copying the state directory
  clones nothing. A TPM clear (`tpm2_clear`, firmware reset, new mainboard)
  destroys the identity: the node enrolls again with a new key.
* **Signing.** `TPM2_Sign` per TLS handshake and once for the device
  certificate. The key stays loaded for the life of the daemon. Expect
  10–100 ms per signature on a discrete chip, far less on fTPM and swtpm;
  a hub pays it once per tunnel, not per packet.
* **Checks at load.** The daemon refuses a blob whose attributes do not
  say TPM-generated, fixed, non-duplicable signing key, and anything but
  P-256. The TPM itself verifies that the public area belongs to the
  private blob.
* Switching an enrolled node from `softkey` to `tpm2` is a new identity: a
  new fingerprint, a new enrollment. There is no import, on purpose.

Code: `internal/devicekey/tpm2key` (part of the TCB), on
`github.com/google/go-tpm`. No cgo, no tpm2-tss.

## Which TPMs

| TPM | `tpm_device` | What `hardware_bound` is worth |
|---|---|---|
| Discrete or firmware TPM of a physical machine (Linux) | default `/dev/tpmrm0` | The key cannot leave the machine, short of a physical attack on the chip |
| **vTPM of a VM**: Proxmox VE "TPM State" (v2.0), libvirt/QEMU `tpm-crb`/`tpm-tis`, VMware, Hyper-V, cloud vTPMs | default `/dev/tpmrm0`; the guest sees an ordinary TPM | The key cannot leave the *VM* from inside the guest: root in the guest, a stolen disk image or a backup of the guest file system does not yield it. Whoever controls the hypervisor can copy the vTPM state together with the VM (on Proxmox the state is a small volume next to the disks, and a clone or backup includes it) |
| swtpm as a process or sidecar | `unix:…` / `tcp:…` | Nothing beyond a software key; lab and tests only |

Proxmox: add "TPM State" (version 2.0) to the VM, boot, check that
`/dev/tpmrm0` exists (kernel modules `tpm_tis`/`tpm_crb`, present in every
current distribution kernel), set `key_kind: tpm2`. The daemon needs read
and write access to the device (root, or group `tss`). Cloning such a VM
clones the node identity: enroll clones with a fresh state directory, and
treat "who may clone VMs and read vTPM state on the host" as part of the
decision to grant `hardware_bound`.

macOS nodes keep a software key until a Secure Enclave backend exists
(MACOS.md); Windows is not a target of the prototype.

## `hardware_bound`: claimed, granted, signed

A node *reports* `key_kind` and `hardware_bound` at enrollment. Nothing
proves that report remotely (see "No attestation" below), so it grants
nothing by itself:

1. **Claimed**: stored as `hardware_claimed`, shown to the admin ("reports
   a hardware key").
2. **Granted**: at confirm the admin decides. The default takes the claim;
   the checkbox in the confirm dialog (API: `"hardware_bound": false`)
   declines it, for example for a vTPM on a hypervisor other people
   administer. Granting it to a node that reported a software key is
   refused.
3. **Signed**: the grant is a field of the binding the admin signs
   (BINDINGS.md). Nodes verify it like roles and prefixes, so a compromised
   control plane cannot declare a software-key node hardware-bound, nor the
   reverse. Changing the grant later drops the approval until the binding
   is signed again.
4. **Used**: policies see the signed value as `principal.hardware_bound`
   (ACL.md), the policy builder offers it as a condition:

```cedar
// production only from machines whose key lives in a TPM
forbid(principal, action, resource in BoundGate::Network::"10.60.0.0/24")
  unless { principal.hardware_bound };
```

## No attestation (yet)

The control plane does not verify that the enrolled key really lives in a
TPM. Doing so needs the TPM's endorsement key certificate, the
manufacturer's CA chain and a credential-activation round trip
(`TPM2_MakeCredential` / `TPM2_ActivateCredential` with an attestation key
that certifies the device key); vTPMs and swtpm have no manufacturer chain
at all. In the prototype the trust anchor is the same as for everything
else at enrollment: an admin who knows the machine compares the
fingerprint and signs. A node that lies about its key gains exactly what
the admin grants it after looking at it. Remote attestation is future
work (SECURITY.md R67).

## Lab and tests

* `make test-tpm` starts a throwaway swtpm container and runs the
  `tpm2key` tests against it: create, reopen (same identity), sign and
  verify, TLS 1.3 client authentication, a damaged or foreign blob does not
  load, and leaked handles of crashed processes do not exhaust the TPM.
  Without `BOUNDGATE_TEST_TPM` the tests skip, so `make test` needs no TPM.
* The compose lab has `node-t` with an `swtpm` sidecar (unix socket in a
  shared volume, TPM state in the volume `swtpm-state`). `make e2e` step 13:
  the node enrolls with a TPM key, `hardware_bound` is granted and signed,
  a policy `when { principal.hardware_bound }` admits `node-t` and refuses
  the software-key `node-r`, the dry run agrees, and a control plane that
  flips the flag in its database gets the node ignored by everyone.
* A raw socket TPM has no resource manager. The daemon flushes all
  transient objects when it opens one, because a crashed predecessor leaves
  its key loaded and a TPM has room for about three. That is safe only
  because such a TPM belongs to this node alone; with `/dev/tpmrm0` the
  kernel does the housekeeping and nothing is flushed.
