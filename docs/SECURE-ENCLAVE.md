# Secure Enclave device keys on macOS (M6.1)

With `key_kind: secure-enclave` a Mac's identity key is created inside its
Secure Enclave and never exists anywhere else. Everything above it is
unchanged: the same self-signed device certificate, the same SPKI
fingerprint, the same mTLS. It is the Mac's counterpart of `tpm2`
([TPM.md](TPM.md)) and reports `hardware_bound` the same way.

```yaml
key_kind: auto              # what BoundGate.app ships with, see below
# key_kind: secure-enclave  # insist: fail to start on a Mac without one
# sekey_helper: /path/to/boundgate-sekey   # default: next to boundgate-node
```

Needs a Mac with a Secure Enclave: Apple silicon, or an Intel Mac with a T2
chip.

## What happens

* **Helper.** The Secure Enclave is only reachable through Apple's
  frameworks, and `boundgate-node` is Go without cgo. The key operations go
  through `boundgate-sekey`, a Swift program of about a hundred lines
  (`apps/macos/Sources/boundgate-sekey`): `create`, `public`, `sign <sha256>`,
  `available`. One process per operation, no state, no decisions. It ships in
  `BoundGate.app/Contents/MacOS` next to the daemon; for an install without
  the app: `make mac-sekey`, then `deploy/macos/install.sh` copies it.
* **Key.** ECDSA P-256, generated by the Secure Enclave
  (`SecureEnclave.P256.Signing.PrivateKey`), this device only, usable after
  the first unlock since boot, **no user presence**: the daemon connects
  unattended. The key binds the machine; the person is OIDC's matter.
* **On disk.** `<state_dir>/device.sekey` (0600): the key *as wrapped by this
  one Secure Enclave* and the public key. No keychain is involved, which is
  why the root daemon (it has no login keychain) can use it. On any other Mac
  the file is useless, and the node says so at start ("was the state
  directory copied from another machine?"). Erasing the Mac or replacing its
  logic board destroys the identity: the node enrolls again with a new key.
* **Signing.** One helper run per TLS handshake and once for the device
  certificate, some tens of milliseconds. The digest goes on the command
  line, the wrapped key on stdin, the daemon's environment is not passed on.
* **Nothing from the helper is taken on trust.** The node checks every
  signature against the public key it enrolled with before using it, checks
  at start that the Secure Enclave still reports that same public key, and
  refuses a helper that is not an absolute path to an executable which only
  its owner can write.

## `auto`, and moving an enrolled Mac over

`key_kind: auto` never changes the identity a node **enrolled with** - it must
not come back from an app update as somebody else. Everywhere else the
hardware wins:

| state directory | result |
|---|---|
| has `device.sekey` | Secure Enclave key |
| has `device.key` and a pinned control plane (`control.pin`, or `control.pin:` in the configuration) | the software key stays, **and the app says so in red on every card**, with a button that moves the Mac over (below) |
| has `device.key`, no control plane pinned (never enrolled, or "Forget this control plane") | Secure Enclave key; the old file is left and no longer used. Before 2026-09-20 the software key won here, silently: a Mac that had once run a development build enrolled with it again |
| fresh | Secure Enclave key where there is one; software key elsewhere, with the same red warning (Intel Macs without a T2) |

A software key on a Mac is never silent: `key_warning` in the daemon's status,
`WARNING:` in `boundgatectl status`, a `SOFTWARE DEVICE KEY` line in the log,
and the red card in the app. The admin sees `softkey` / `hardware_bound: false`
in the request and decides.

To move a Mac that enrolled with a software key:

```bash
boundgatectl down
boundgatectl reset -new-identity     # forgets the control plane AND the device key
boundgatectl configure -control vpn.example.com
boundgatectl enroll                  # new fingerprint: confirm and sign it again
```

and revoke the old node in the admin UI. The confirm dialog then offers
"Hardware-bound", because the node reports a hardware key.

## What this does and does not give

The key cannot be copied off the Mac: not from a backup, not by malware, not
by root. That is the whole claim. It does **not** mean a person approves each
use - whoever is root on the Mac can have the Secure Enclave sign for as long
as he is on the machine (R86), as with a TPM key without authorization (R69).
And the control plane has the node's word for the key kind: there is no
attestation (R85); `hardware_bound` is what an admin who knows the machine
grants and signs (R67).

## Verified

`internal/devicekey/sekey` is tested on every platform with the test binary
standing in for the helper (create/load, TLS 1.3 client authentication, a
helper that signs with another key, a foreign blob, a swapped public key, the
helper path checks). With the real helper on Apple silicon (2026-09-20): a
signature over a given digest verifies with `openssl dgst -verify`; an ad hoc
signed helper and one with the hardened runtime both reach the Secure
Enclave; `boundgate-node` with `key_kind: auto` on a fresh state directory
comes up as `secure-enclave`, `hardware_bound: true`, and with the same SPKI
after a restart. Not yet tried by hand: the daemon as root under launchd
before anybody has logged in.
